# 32 GB NAND investigation — P105AP / iPad2,5

**Date:** 2026-11-21  
**Status:** read-only research and historical incident record. **Do not flash, resize, mount read-write or repair the physical device on the strength of these findings.**

## Executive summary

A real Wi-Fi iPad mini 1 (A1432, `iPad2,5`, `p105ap`), running jailbroken iOS 8.4.1 (`12H321`), has **32 GB-class internal NAND** and successfully boots a Cascadia-derived Alpine RAM image from its existing iOS System partition. The initial **NAND-backed Linux volume attempt did not complete**; that is a separate, unresolved track.

The upstream [Project Cascadia](https://github.com/rzxvx/Project-Cascadia) NAND installer and LwVM planner are based on a **16,000,000,000-byte** reference device. The tested local device's LwVM header declares **32,000,000,000 bytes**. A 32 GB media case changes the LwVM chunk addressing scheme, not just an equality check. The local Gemini-edited source files and simulator tests are not yet a reviewed, reproducible 32 GB installer.

| Local diagnostic | `nand-volume.sh diagnose --live` -> **NOT READY (BLOCKED)** | PPN firmware, physical NAND block/CAU geometry, and safe writer compatibility unverified |
| Independent OS boot | `root=/dev/ram0` on device, Wi-Fi/SSH/shell working | Does not depend on a writable Linux NAND partition |

The previous failed installer left **uncertainty** about whether a low-level header operation had been interrupted. Do not state that the device's NAND has never been touched. The subsequent PC-less installation *did* write six boot artifacts to the **iOS System filesystem via iOS**, but did not create a Linux NAND volume.

No unique serial, chip identifier, SSID, private address, credentials, NAND dumps, or firmware is stored here.

## Why the 16 GB LwVM implementation is not directly portable

The upstream source as inspected on 2026-11-21 contains:

- [`devices/a5/tools/nand-volume/lwvm.py`](https://github.com/rzxvx/Project-Cascadia/blob/main/devices/a5/tools/nand-volume/lwvm.py): `MEDIA = 16000000000`, `CHUNK = 16 << 20`, `NCHUNKS = MEDIA // CHUNK`. The header parser **rejects other media sizes**.
- [`devices/a5/patches/files/drivers/mtd/nand/apple/sftl_lwvm.c`](https://github.com/rzxvx/Project-Cascadia/blob/main/devices/a5/patches/files/drivers/mtd/nand/apple/sftl_lwvm.c): `CHUNK_LBAS = 4096` and 4 KiB logical sectors, again implying **16 MiB** chunks for address translation.
- [`sftl.h`](https://github.com/rzxvx/Project-Cascadia/blob/main/devices/a5/patches/files/drivers/mtd/nand/apple/sftl.h): the chunk map is limited to **1024 entries**.
- [`nand-volume.sh`](https://github.com/rzxvx/Project-Cascadia/blob/main/devices/a5/tools/nand-volume/nand-volume.sh): a hardcoded `BOUND=15854493696` matching the 16 GB geometry.

For a 32,000,000,000-byte LwVM medium, 16 MiB chunks would require about **1,908** entries, exceeding the 1024-entry on-disk map. Thus changing `MEDIA` alone is **insufficient** and can cause incorrect partition-to-physical translation.

An independent historical implementation, [openiBoot `bdev.c`](https://github.com/iDroid-Project/openiBoot/blob/master/bdev.c), derives the LwVM chunk shift from the header's `mediaSize`:

```c
LwVM_rangeShiftValue = 32 - __builtin_clz((mediaSize - 1) >> 10);
LwVM_rangeByteCount = 1 << LwVM_rangeShiftValue;
```

Applied to these nominal sizes:

| Media size | Calculated shift | Chunk size | Approximate chunk count |
| ---: | ---: | ---: | ---: |
| 16,000,000,000 bytes | 24 | 16 MiB | 954 |
| 32,000,000,000 bytes | 25 | 32 MiB | 954 |

*Numbers above are derived from the openiBoot formula, not measurements of this unit's actual map.* The design question for the Linux LwVM implementation is how every chunk index, offset and boundary is derived and validated from the real header, rather than from 16 GB constants. The reported prior local tests of dynamic-size changes are welcome but still do **not** prove NAND safety.

Another independent primary record, [an iOS 8.4.1 ARMv7 IOMedia dump](https://github.com/arx8x/iOS-IOMedia-IOKit-dumps/blob/master/IOMedia_iOS_8.4.1_HFS_armv7_home_depot.ioreg), shows an actual iOS LwVM stack reporting `disk0 Size = 32000000000` and 4 KiB blocks. **It does not identify our exact iPad model or demonstrate any Linux NAND install.**

## Beyond chunk geometry: critical blockers

1. **Duplicate header consistency:** The device formerly reported divergent LwVM copies. Diagnose both logically and against iOS's own validator before attempting any recovery or installation.
2. **FTL/PPN topology:** A second physical NAND geometry may imply different erase block counts, die/bus/CAU distribution, metadata assumptions, free space and wear-leveling behavior. An LwVM-only unit test proves none of these.
3. **Global metadata hazard:** Cascadia explains that the flash translation layer updates a disk-global block map. An error can affect iOS's partitions and the jailbroken kDFU recovery route, not only an intended Linux volume.
4. **iOS HFS+ shrink and LwVM writer:** Capacity-aware arithmetic must cover both partition boundaries and iOS filesystem shrink, as well as driver reads/writes and mount/recovery. A validated Python header serializer alone is insufficient.
5. **Recovery:** A host-side recovery path, with verified snapshots and expected post-recovery outcomes, is a prerequisite to any write trial. The ability to read a header is not a proven recovery strategy.

The upstream [Quickstart](https://github.com/rzxvx/Project-Cascadia/blob/main/devices/a5/docs/QUICKSTART.md) explicitly warns that its NAND mode changes the partition table and iOS's FTL. It was validated on its maintainer's hardware and **does not document an independently verified 32 GB installation**.

Searched public GitHub code, issues, commit history, related repositories and selected forks for `32GB`, `32 GB`, `32000000000`, `iPad2,5`, `LwVM` and Cascadia. **No independently verifiable report or patch showing a successful 32 GB P105AP Cascadia NAND-backed installation was found.** This is a search limitation, not proof none exists.

- [openiBoot LwVM dynamic chunk calculation](https://github.com/iDroid-Project/openiBoot/blob/master/bdev.c): useful independent implementation, not a P105AP NAND safety certificate.
